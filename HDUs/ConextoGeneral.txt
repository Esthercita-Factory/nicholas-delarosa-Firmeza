Proyecto Firmeza: resumen de las Historias de Usuario del Módulo 6.3

El proyecto consiste en desarrollar un sistema para una empresa dedicada a la venta de materiales de construcción y al alquiler de vehículos. El trabajo se desarrolla por etapas a lo largo de cinco semanas: módulo administrativo, importación y exportación de datos, API, módulo del cliente y, finalmente, pruebas automatizadas con despliegue en Docker. Cada historia de usuario tiene un valor de 20 puntos.

Semana 1. Módulo administrativo base
Se crea la solución vacía Firmeza y, dentro de ella, un proyecto ASP.NET Core con Razor Pages (versión 8 o superior). Se instalan Entity Framework Core con Npgsql, Identity, EPPlus y QuestPDF o iTextSharp; los dos últimos quedan instalados para uso posterior. La base de datos en PostgreSQL debe construirse exclusivamente mediante migraciones, sin scripts SQL manuales. Se modelan las entidades del negocio (productos, clientes, ventas y detalle de ventas) y se configura Identity con dos roles: Administrador, que accede al panel, y Cliente, que debe ser bloqueado o redirigido si intenta ingresar. El panel incluye una barra lateral de navegación, un dashboard con métricas básicas, el CRUD de productos con búsqueda y filtrado, y el CRUD de clientes con validación de correo, documento y teléfono. También se exige manejo de errores con try-catch, un diseño visual coherente y documentación con README, diagrama entidad-relación y diagrama de clases. De forma opcional, se sugiere una prueba unitaria con xUnit y un borrador de los archivos de Docker.

Semana 2. Carga masiva, exportaciones y recibos PDF
Se implementa la importación de archivos Excel con datos desnormalizados mediante EPPlus. El sistema debe identificar a qué tabla corresponde cada columna, normalizar la información en memoria, validar los campos obligatorios, insertar o actualizar los registros y generar un registro de errores. Además, se debe permitir la exportación de productos, clientes y ventas a Excel y PDF. Al registrar una venta, el sistema genera automáticamente un recibo en PDF con los datos del cliente, la fecha, el número de venta, la lista de productos, los totales y el IVA; este recibo se almacena en la carpeta wwwroot/recibos y puede descargarse desde la interfaz. Se mantienen las tareas de diseño y documentación, y las pruebas y Docker siguen siendo opcionales.

Semana 3. API REST
Se agrega a la solución un proyecto ASP.NET Core Web API conectado a la misma base de datos del módulo administrativo. Se configura Identity junto con autenticación JWT, se crea el rol Cliente y se definen políticas de autorización que distingan entre administradores y clientes. Se implementan AutoMapper y DTOs para productos, clientes y ventas, y controladores con operaciones CRUD completas que respondan siempre con DTOs. La API debe documentarse con Swagger, incluyendo soporte para autenticación JWT. Asimismo, se configura un servicio de correo real mediante SMTP de Gmail, diseñado de forma desacoplada para poder reemplazarlo en el futuro por un servidor empresarial. Finalmente, se crea el proyecto Firmeza.Tests con al menos una prueba unitaria exitosa. El Dockerfile de la API es opcional.

Semana 4. Módulo del cliente
Se crea un proyecto frontend (React, Angular, Vue, Next.js u otro) dentro de la solución, que se ejecute de forma independiente en su propio puerto y consuma la API. La autenticación se realiza con JWT: el token se almacena en LocalStorage o SessionStorage, se envía en la cabecera Authorization de cada solicitud y, cuando expira, el usuario es redirigido al inicio de sesión. El frontend solo debe consumir los endpoints del rol Cliente: registro, inicio de sesión, consulta de productos, creación de ventas y descarga del comprobante. Se desarrollan las vistas de registro, inicio de sesión, catálogo de productos y carrito de compras, con cálculo automático de subtotal, impuestos y total. Tras la compra, la API envía el comprobante en PDF al correo del cliente y el frontend muestra un mensaje de confirmación. La interfaz debe ser adaptable, mostrar el nombre del cliente autenticado y permitir cerrar sesión. Se requiere documentación y al menos una prueba unitaria.

Semana 5. Pruebas automatizadas y despliegue con Docker
Se consolida el proyecto Firmeza.Tests con pruebas de lógica de negocio, servicios o validaciones. Se crea un Dockerfile para las pruebas que restaure, compile y ejecute dotnet test, finalizando con un código de salida distinto de cero si alguna prueba falla. También se crea un Dockerfile de producción para cada proyecto: Admin, API y Client. En la raíz de la solución se define un archivo docker-compose.yml que ejecute primero las pruebas y, solo si estas resultan exitosas, levante la base de datos PostgreSQL, la API, el módulo administrativo y el cliente. Toda la solución debe iniciarse con el comando docker compose up --build, sin necesidad de abrir un IDE ni ejecutar servidores manualmente.


Observaciones
En la Semana 1, la tarea 7 menciona la validación de una edad, aunque ninguna entidad la incluye; se recomienda aplicar esa validación a campos como cantidades, precios o documento. En la Semana 3, la tarea 6 menciona ViewModels, aunque en la API corresponde usar DTOs, y la tarea 8, titulada "gestión de clientes", trata en realidad sobre el servicio de correo SMTP. Por último, el proyecto Firmeza.Tests aparece en varias semanas, pero se trata de un único proyecto que se amplía progresivamente.
